# Promotion Decision and Application

## 1. Entry Conditions

Use after a Candidate is frozen and the user explicitly requests a decision or action.

Application, limited application, retention, and rollback each require an unambiguous human instruction. Review or acceptance of a Candidate does not itself authorize modification of the active library.

## 2. Required Inputs

- the frozen `candidate_patch.json` and `candidate.patch`;
- the target repository or library root;
- explicit reviewer identity or stable reviewer label;
- decision and rationale;
- for application: required post-apply validation commands or Workflow validation plan;
- for retention or rollback: the current `promotion_record.json` and decisive validation evidence.

## 3. Decision Procedure

1. Record one of: `apply`, `apply_limited`, `revise`, `reject`, or `defer`.
2. For `revise`, `reject`, or `defer`, leave the active library unchanged.
3. Before application, verify Candidate status, patch hash, target paths, current base hashes, and `git apply --check`.
4. Apply the exact frozen patch as one atomic change set only after explicit authorization.
5. Record pre/post target hashes and actual apply result.
6. Run the declared structural, syntax, schema, import, unit, and target-specific validation that is applicable. Save logs only for commands actually executed.
7. Record post-apply validation separately from Candidate replay validation.
8. Retain only after explicit human retention. Use `retained_limited` only with an explicit limited decision and stated scope/evidence limitations.
9. On explicit rollback, reverse the same frozen patch, verify restoration of base hashes, and record the rollback result.
10. Do not commit, merge, or push unless separately and explicitly requested outside this Skill contract.

## 4. Output Contract

Write or update:

```text
<evolution_root>/decisions/<promotion_id>/promotion_record.json
```

Actual apply/validation command logs may be written under:

```text
<evolution_root>/decisions/<promotion_id>/logs/
```

No separate merge record, rollback patch, validation report, retention report, or status file is generated by default.

The Promotion record must validate against `schemas/promotion_record.schema.json`.

## 5. Completion Conditions

- the human decision is explicit and recorded;
- unauthorized decisions leave the active library unchanged;
- application uses the exact frozen patch and matching base hashes;
- post-apply validation truthfully records passed, failed, limited, blocked, or not-run evidence;
- retention or rollback is explicit;
- rollback restores declared base hashes when executed.

## 6. Invariants

- No automatic promotion, application, retention, merge, commit, push, or rollback.
- `apply_limited` must include explicit limitations.
- Applied does not mean validated; validated does not mean retained.
- Failed validation must not be reported as retained.
- Rejection, revision, or deferment preserves the active library.
- Rollback uses the same Candidate patch in reverse and remains evidence-linked.

## 7. Failure Routing

- Candidate not frozen or hash mismatch → return to Candidate;
- target base changed → defer or create a new Candidate against the current base;
- apply check failed → record application failure and do not modify targets;
- post-apply validation failed → record `blocked` and request explicit rollback or revision;
- rollback check failed → record blocked rollback and preserve evidence for manual review;
- insufficient evidence for full retention → retain only with explicit limitations, defer, or roll back.

## 8. Scripts

- `scripts/record_decision.py`: create the canonical Promotion record without changing target files;
- `scripts/apply_candidate.py`: verify authorization and hashes, apply the exact patch, run declared post-apply validation commands through `--validation-argv-json` or `--validation-command`, and update the Promotion record;
- `scripts/record_retention.py`: record explicit retain, retain-limited, or blocked status;
- `scripts/rollback_candidate.py`: reverse the exact patch, verify restoration, and update the Promotion record.
